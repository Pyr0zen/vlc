## 2026-10-13 performance: settings sidebar effects and the resume lookup (worktree, not built yet)
- Settings sidebar sliders did UI-thread work that scales with the page, not with the change: about 100 bindings read `(RdEffects.revision, RdEffects.xxx(...))`, every setter (each step of a drag) bumped the one revision, and each binding then took the player lock (getVout / getAout), read vout / aout variables and the configuration and parsed strings on the UI thread. config_SaveConfigFile also ran on the UI thread 500 ms after the last change (5-50 ms, possibly mid-drag). Fix: RdEffects caches every value in a QQmlPropertyMap (`RdEffects.values`), one property per key, so a binding follows only its own value and reads it without a lock: `RdEffects.values[RdEffects.videoKey("hue")]`; the ...Key() functions read a value from VLC the first time it is asked for; equalizerPreset, equalizerBands, subtitleTextScale and subtitleDurationFactor always exist. A setter updates its cached value at once and queues the change; queued changes reach VLC in call order, at most once per frame (16 ms, consecutive steps of the same change merged), then the values they touched are read back from VLC. The cache is re-read by refresh(), when the video outputs change and when a sidebar page is shown. The file is saved on a worker thread (config_SaveConfigFile is serialized by its own static lock and reads values atomically under RCU, src/config/file.c); string options set during a save are held back until it ends, since config_PutPsz calls vlc_rcu_synchronize and would wait for it. The destructor applies the last queued changes and waits for the save; VLC writes the file again when it quits (config_AutoSaveConfigFile).
- Compatibility: option(), the other getters, setOption(), optionChoices(), optionRange(), optionDescription(), refresh() and `revision` keep working; the getters return the cached values and `revision` changes once per apply and on refresh() (no binding of this branch reads it any more). The Video, Audio and Subtitles sidebar pages and the Settings dialog's Subtitles page now use the per-key form. Other branches should migrate `(RdEffects.revision, RdEffects.option(n))` to `RdEffects.values[RdEffects.optionKey(n)]`.
- Checked offscreen with PySide6 6.8.3 before any build: a QQmlPropertyMap key inserted from a Q_INVOKABLE called inside the binding that reads it gives a working per-key dependency (only that binding re-evaluates; keys added later, from later components, also work).
- Resume prompt: the redesign's resume position lookup (vlc_ml_get_media_by_mrl, SQLite) ran on the Qt main thread at every file open. It now runs through MediaLib::runOnMLThread and the prompt state is set in the UI callback (the toast appears once the position and the 20 s rule are known, as before); a query whose media was replaced or stopped meanwhile is ignored (m_restoreQuery).
- To check on the build: drag every sidebar slider (equalizer bands and preamp, compressor, video adjust, subtitle duration, font size) with QSG_RENDER_TIMING=1: 60 fps, the effect follows live; Flip None / Horizontal / Vertical and Rotate; toggling filters on and off, Wall then Clone (one splitter at a time); equalizer preset then a band, None then a band (turns the equalizer on); settings survive a restart; change a value in VLC's Effects dialog, then open the sidebar page (shows the new value); open files with and without a saved position, and one watched to its last 20 s; quickly switching files does not show a stale prompt.

## 2026-10-15 bug: subtitle speed / timing froze the video, audio kept playing (worktree, not built yet)
- Sticky: "when changing subtitles speed and timing it freezes the video but the audio keeps playing".
- Cause (core path, read in the source): "Subtitle Speed" is VLC's sub-fps (vlc_player_SetAssociatedSubsFPS, player.c:1209, INPUT_CONTROL_SET_SUBS_FPS, RequestSubRate input.c:974). For an external subtitle file with a video that reports its fps (mp4, mkv, avi) every new value changes slave_subs_rate, and SlaveDemux (input.c:3145) then sends ES_OUT_RESET_PCR: EsOutChangePosition (es_out.c:1161) flushes every decoder, video and audio included, resets the clocks and rebuffers. The audio restarts after a few ms; the video decoder starts again from inter frames and has nothing clean to show until the next keyframe (frozen or smeared picture for up to a GOP). The sidebar slider set the fps on every mouse move, so a drag kept the video frozen. Stock VLC does the same once per spin box step (Adjustments and Effects > Synchronization > Subtitle speed).
- Subtitle Track Delay: the core path is cheap (vlc_player_SetCategoryDelay > es_out SetDelay > decoder delay > vout_ChangeSpuDelay > SPU channel clock delay; no flush, no rebuffer; a negative delay only raises the input pts delay). Still sent on every mouse move with an OSD text each time: now at most every 100 ms while dragging and on release.
- Subtitle Duration Factor: subsdelay-factor is a command variable of the subsdelay sub filter, proxied by the vout (filter_AddProxyCallbacks): live, cheap. Crossing 0 during a drag switched the filter off and on (sub-filter chain rebuilt on the next subtitle, displayed subtitles lose their extended duration). Not a video stall, but now the filter is switched off only when released at 0.
- Mapping and labels (Sticky's screenshot: "1.000 fps", thumb at the far left; Duration Factor "0.000" far left): correct and as in the video 7:16-7:23 (rows 92/94: "Subtitle Speed 1.000 fps", "Subtitle Duration Factor 0.000", both thumbs at the far left) and VLC's Synchronization tab: sub-fps is the frame rate the subtitle file was timed for (1 to 100 fps), and 1 fps (or less) means the file's own timing, so the default sits at the left end. ## 2026-10-15 waveform scan hang on MP3 (HIGH, build 38800817536; fix not built yet)
- Bug: with a 3 min 192 kbit/s MP3 playing, switching Playback > "Show Waveform on Seekbar" on showed no waveform, the log had no "waveform scan" / "waveform: ready" line, and Ctrl+Q left VLC "Not responding" (about 167 s of CPU, force-closed).
- Cause: `RdWaveformScanner::Scan::process()` (rd_waveform_scanner.cpp, the packetizer loop) released the input block after `pf_packetize()` and in its two error paths. A packetizer owns the block it is given: a bytestream packetizer (MPEG audio, also AAC, FLAC, A52 ...) pushes it into its queue and leaves `*pp_block` pointing at it, and the input core never releases it. So every MP3 block was freed while still queued: a use after free / double free that corrupts the packetizer's block chain; the next block of the same size reuses the freed memory, the chain loops on itself and the packetizer spins forever inside `pf_packetize()`, where the scan's cancel and stop checks are never reached. The scan never ended (no log line, no bars), and `~RdWaveform` waited for it with an unbounded `QThreadPool::waitForDone()` on the GUI thread: the hang on quit. The PC tests of the branch used WAV and PCM-in-MOV only, whose copy packetizer clears `*pp_block`, so they never hit it.
- Fix: `process()` never releases the block it hands the packetizer (as the core's decoder loop) and always lets the packetizer finish the block; once the scan stops (cancel, failure, time budget), packets are dropped instead of decoded. A hard time budget of 60 s per scan (`RdWaveformScanner::kTimeBudgetSeconds`, checked at every packet and decoded frame; over it the file gets no waveform, cached like an unusable file). `~RdWaveform` waits at most 500 ms (`kQuitWaitMs`) for a cancelled scan, then leaves the pool to the process's end with a warning instead of hanging; the scan's VLC objects now hang from the libvlc instance, which outlives the interface. New log line `waveform: job started for the playing file` when the job starts, so a test shows whether the option reached the scanner.
- Checked by reading: the option turned on mid-playback starts the job at once (acquire() -> startScan(), the length is already known), but only for a thick seek bar (control bar time text Inline); the scan runs on the pool thread only; cancel sets the flag and kills the scan's VLC interrupt. ## 2026-10-16 mouse wheel on sliders, wheel never through overlays (Decision 51; worktree, not built yet)
- Asked by Sticky: the wheel over a slider's bar or tick-label row fine-tunes it in small exact steps, and the wheel over any popup, panel, sidebar, menu or dialog must never reach the player's wheel handler (volume / seek).
- The player's wheel: `VideoSurface::wheelEvent` (maininterface/videosurface.cpp) accepts every wheel event and sends it through `WheelToVLCConverter` to the vout as a key press, where VLC's hotkeys apply the wheel modes (hotkeys-y-wheel-mode / hotkeys-x-wheel-mode: volume, seek); the audio-only view does the same in Player.qml (`centerContent` MouseArea -> MainCtx.sendVLCHotkey); Ctrl+wheel is the window-level interface zoom (InterfaceWindowHandler). Qt Quick hands the wheel to every item under the pointer, top first, until one accepts it; plain Items and Rectangles ignore it, so any card without a wheel-taking item let it fall through to the video. Bug (MED): mini player, compact library while it slides in over the video, resume toast; outside an open RdMenuPanel the wheel also reached the player. Player.qml, TopBar.qml and MainInterface.qml are unchanged.
- Sliders: new widgets/qml/RdSliderWheel.qml (a MouseArea that takes no buttons and no hover) fills every RdSlider (its item is exactly the bar plus the label row; the name row of RdParamSlider is outside it, so the wheel there scrolls the page). Wheel notches of 120 angle units; high-resolution wheels and touchpads add up their fractions (angleDelta, or pixelDelta at 24 px per step when only that is sent; the remainder is dropped after 400 ms without wheel or on a change of direction); natural scrolling (`inverted`) is turned back to the finger direction; up or right increases, right decreases on a mirrored slider like the arrow keys. Every wheel event over a slider is taken, also at its ends (it never scrolls the list or reaches the player), except while a list holding it is scrolling (an ancestor's `moving`) and for the rest of that wheel gesture (events less than 400 ms apart): then it passes to the list, so scrolling the sidebar does not stop on the first slider under the pointer.
- RdEndlessSlider (every RdParamSlider and SettingsOption slider): `wheelStep` (default `step`) and `_wheelMove`: the value moves on the multiples of the wheel step from rangeFrom (a value between two goes to the next one in that direction first, rounded to 1e-9 so no float residue), past the normal range up to VLC's limits like the arrow keys, through `_show` (the scale scrolls, slides home back in range) and `valueMoved`, the same signal as a drag or key step. Plain RdSlider: T.Slider increase() / decrease() by stepSize (as its arrow keys; the value binding stays) and moved(). The Settings dialog equalizer bands (T.Slider) use the same RdSliderWheel.
- Pacing: the wheel is not a press, so RdSliderCommit treats each notch as a key step: committed `keyDelay` ms after the last notch (subtitle delay 150 ms, audio delay 300 ms, subtitle speed 400 ms, duration factor 150 ms, pitch 150 ms, non-live video filter parameters 300 ms); sliders that apply a drag at once (Speed, Font Size, equalizer, audio filters, live video filters, Settings dialog options) apply each notch at once, exactly as a drag step. Nothing reaches VLC faster than a drag does.
